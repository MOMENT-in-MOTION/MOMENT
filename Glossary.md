

# Glossary

## Term: Model 
Usage: An Abstract representation of a Topic, generally simplified. Usually generated for some use case scenario, like calculation or to make categorical statements. Think of a model of the Solar system, or the atomic shell model.

## Term: View  
Usage: Any visual representation of a model, be that a graph, a textual description, an api or even a resin cast.  
Notable Examples: Json representations of models, Class Diagrams and most notably APIs

## Term: Meta-Model  
Usage: A Model made to describe Models, generally used as a Categorisation tool, for “all models following this blueprint” type statements. Notably a Meta-Model is also a Model while not every model is a Meta-Model. In our work most Models mentioned utilised will be Meta-Models describing some sets of use case specific models.

## Term: Meta-Meta-Model  
Usage: A Model made to describe Meta-Models as a group, usually focused on the core building blocks that make models. Therefore a Meta-Meta-Model is akin to a Modeling language. By definition a Meta-Meta-model is also a Model as it is made to be congruent to it’s own syntax rules.  
Notable Examples: Our Parser runs on a Meta-Meta-Model.

## Term: API  
Usage: A library of functions and Objects, that form the basis for codeing work with a particular model. It is to be understood as a view on the model in question.  
Notable Examples: Our Parser outputs APIs

## Term: Parser  
Usage: Software component that reads JSON views of models and generates an internal representation Based on them

## Term: Merger  
Usage: Software component that works in conjunction with the parser to add Secondary Models onto the existing initial parsed representation

## Term: Secondary Model
Usage: A view of a Meta-Model in JSON format, that isn't the primary argument for code generation yet is still relevant for the process. Most commonly as the Model is references within the Primary Model

## Term: Primary Model
Usage: A view of a Meta-Model in JSON format, that is used as the primary argument for MOMENT and is the first to be parsed. All Secondary Models are referenced ether by the Primary model or by a Secondary model.

## Term: Import Mode
Usage: The specific method the Merger uses to integrate Secondary Model views
Notable Examples: "merge" mode and "import" mode

## Term: "merge" mode
Usage: An Import mode in which the Merger will fully read and integrate Secondary models into the internal representation.

## Term: "import" mode
Usage: An Import mode in which the merger references Secondary models as existing packages, they aren't added to the internal representation but are referenced by the resulting API by use of import statements.

## Term: import_link
Usage: a reference to a Secondary Model ether a file path to a json file (in "merge" mode) or a module name [package.model] (in "import" mode)

## Term: internal representation 
Usage: Effectively another view on a Model. Specifically one that is created during runtime and isn't intended to be revealed to users
Notable Examples: the result of the parser and merger is an internal representation

## Term: Mapper  
Usage: Software component that turns an internal representation into a mapping (arguably a secondary internal representation) for Code-generation

## Term: Mapping
Usage: A list of instructions that is read by the Code-generator to generate an API.
Notable Examples: the output of our Mapper

## Term: Code-Generator 
Usage: A software component that outputs functional Code, In our project this will be an API. Our Code-generator does so by use of the Jinja2 Template engine.

## Term: Template
Usage: A building plan for creating text, defining both structure and content, light logic can be included (variables, loops, if-else, etc) 
Notable Examples: The Jinja templates used by our code-generator

## Term: Serialiser  
Usage: A software component serialising an instance of Classes (Notably those generated by our API) into a serialised file, In our case specifically in XML or json format.

## Term: de-serialiser
Usage: utilises a serialised file and an API to recreate the originally serialised instances of classes, effectively reversing the serialisation process.

## Term: serialised file
Usage: a file containing all the information about a specific instance of a class or classes.
Notable Examples: the output of our serialiser as well as the input for our de-serialiser is one of these files.

## Term: Unreachable-Class
Usage: A class that has no reference chain to the root class.

## Term: native Inheritance
Usage: Inheritance implementation using Pythons pre-existing inheritance functionality

## Term: manual Inheritance
Usage: Inheritance implementation merging a class with its superclass effectively recreating the super class as part of the class inheriting from it.

## Term: Association
Usage: Any reference from one class to another, Notably Composition and Reference are Associations

## Term: Composition
Usage: class association in which one class is seen as a part of another, like fingers of a hand.

## Term: Reference 
Usage: class association in which both classes are seen as distinct things that still need each other to function, like a cat and it#s feeding spot.
